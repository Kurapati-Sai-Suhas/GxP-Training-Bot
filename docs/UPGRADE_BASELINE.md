## 3. ⚠️ DATA REALITY — the finding that governs the roadmap

Measured directly from the database at freeze time. **This is the single most consequential
finding of Phase 0**, because it determines whether Phases 9–16 (knowledge tracing) are viable at
all.

| Quantity | Value |
|---|---|
| Learners (non-staff) | 9 |
| SOP documents | 8 |
| Chunks (concept proxy) | 20 |
| Questions (total / approved) | 103 / 64 |
| Questions with `source_chunk` | 87 |
| Completed quiz attempts | 25 |
| **Total interactions (`AttemptAnswer`)** | **60** |

**Interactions per learner**

| Learner | Interactions |
|---|---|
| `demo_learner` | 36 |
| `rohit` | 15 |
| `Suhas` | 6 |
| `priya` | 3 |

Repeated (learner, question) exposures: **11**.

### 3.1 What this means

Published knowledge-tracing models were fitted on datasets of a fundamentally different order:

| Model | Typical training data |
|---|---|
| DKT (Piech et al., 2015) | ~500k–1M+ interactions |
| SAKT / SAINT / AKT | 10⁵–10⁷ interactions |
| BKT (per skill) | Hundreds of interactions per skill, minimum |
| FSRS published weights | ~2×10⁸ reviews |

This repository holds **60 interactions in total**, with a maximum of **36 for a single learner**,
and much of that is synthetic demo data generated by `demo_adaptive`.

That is **three to four orders of magnitude** below the requirement for any neural
knowledge-tracing architecture. It is also below the practical threshold for BKT or a logistic
model such as PFA. This is not a "collect a little more data" gap; it is categorical.

### 3.2 A second, structural blocker — independent of volume

`AttemptAnswer` carries only:

```
id · attempt · question · selected_option · is_correct
```

There is **no per-interaction timestamp** and **no response latency**. Consequences:

- Interaction ordering currently relies on `-id` (auto-increment) as a proxy for time.
  Correct in practice today, but not a temporal guarantee.
- Only `QuizAttempt.completed_at` carries time, at *attempt* granularity — not per answer.
- Forgetting cannot be modelled at the interaction level; only FSRS's attempt-level state exists.
- Models requiring elapsed-time or latency features (SAINT+, context-aware KT, forgetting-aware
  KT) **cannot be fed**, regardless of how much data were collected.

**Conclusion:** even if 500k interactions existed today, the event log lacks the fields those
architectures consume. The correct first action is not to research Transformers — it is to build a
KT-ready interaction event log so that valid data becomes collectable.

## 4. Current architecture — as implemented

### 4.1 Stack

| Layer | Technology (verified) |
|---|---|
| Backend | Django 5.2.15, Django REST Framework 3.17.1 |
| Frontend | React 18.3, Vite 5.4 |
| Database | PostgreSQL (`psycopg` 3) or SQLite, via `DATABASE_URL` |
| Queue | Celery 5.3 + Redis 5 — invoked `.delay().get()`, i.e. process isolation, not async |
| AI | NVIDIA NIM via `openai` SDK (OpenAI-compatible endpoint) |
| Extraction | PyMuPDF (PDF), python-docx (DOCX) |
| Production | Gunicorn + WhiteNoise |

**Models in use**

| Purpose | Model |
|---|---|
| Question generation, SOP chatbot | `meta/llama-3.1-8b-instruct` |
| Semantic chunking (fallback tier only) | `nvidia/nv-embedqa-e5-v5` |

### 4.2 Django apps

`accounts` · `sops` · `quiz` · `ai_engine` · `attempts` · `analytics` · `audit`

### 4.3 Document pipeline (as built)

```
SOP upload → validation (extension, 20 MB) → PyMuPDF extraction
  → chunk_text() three-tier cascade:
        tier 1  heading regex           (used by SOP-DEMO)
        tier 2  Max-Min semantic (embeddings, threshold 0.5, max 1200 chars)
        tier 3  fixed-length
  → SOPChunk rows, chunking_strategy recorded per chunk
```

### 4.4 Generation pipeline (as built)

```
one chunk per prompt → llama-3.1-8b-instruct → JSON → schema normalisation
  → lexical near-duplicate check (answer ≥0.8 AND stem ≥0.4)
  → Question(status="draft", source_chunk=FK)
  3 retries with backoff, then deterministic offline generator (answer lifted verbatim)
  failures classified into 9 categories
```

### 4.5 Adaptive engine (as built)

```
AttemptAnswer.is_correct  (the only raw signal)
  → history per chunk, newest-first
  → weighted_accuracy:  w_i = 0.5^(i/5)          [RECENCY_HALF_LIFE = 5]
  → _classify, in fixed order:
        1. answered == 0            → HIGH   (never assessed)
        2. mastery == "mastered"    → NONE   (streak of 3)
        3. answered < MIN_EVIDENCE(3) and weighted ≥ 60 → MEDIUM (capped)
        4. < 60 → HIGH ;  < 80 → MEDIUM ;  else LOW
  → selected_for_retraining = priority in {HIGH, MEDIUM}
  → available_now = selected AND is_due          [is_due from FSRS]
```

Supporting components: **Elo** (learner K=32, question K=16, both from 1500) and
**FSRS-4.5** (17 published weights, retention 0.9, min interval 1 day; only AGAIN/GOOD grades used).

**New limitations identified during Phase 0:**

| # | Limitation | Evidence |
|---|---|---|
| **L12** | **`AttemptAnswer` has no timestamp and no response latency** — interaction ordering relies on `-id`; KT architectures requiring temporal features cannot be fed | Model field list, §3.2 |
| **L13** | **No embedding persistence.** Embeddings are computed in memory for semantic chunking and discarded. No vector store, no index, no `embedding_model` / `dimension` / `version` metadata | No embedding field on any model; no vector library in dependencies |
| **L14** | **SOP chatbot retrieval is lexical**, not vector-based — `select_relevant_chunks()` scores by word-set intersection. Describing it as "vector RAG" would be inaccurate | `ai_engine/services.py:252` |
| **L15** | **No concept / knowledge-component layer.** The adaptive unit is the physical chunk. Two chunks covering the same concept are tracked independently, and mastery does not transfer | `ChunkMastery` keyed on `sop_chunk` |

## 6. Current RAG / retrieval workflow — precisely stated

```
question text
  → _significant_words()            set of lowercase word tokens
  → for each chunk: |question_words ∩ chunk_words|
  → sort by overlap, ties keep document order
  → top 6 chunks → prompt → llama-3.1-8b-instruct
```

**No embeddings. No vector index. No reranking. No metadata filtering.**

This is defensible at current scale — retrieval operates over a single SOP's chunks (3 in the demo,
20 across the corpus), where an index would be pure overhead. It is recorded here so the upgrade is
measured against what actually exists rather than an assumed vector pipeline.

interactions in total and the event log carries no timestamps.** Any roadmap that begins with
neural knowledge tracing or a vector database would be optimising the wrong end of the system.
