# Knowledge-Tracing Data Readiness

**Measured:** 19 August 2026, immediately after Batch A+B.
**Purpose:** state honestly what learner-interaction data exists, what is temporally usable,
and what any future knowledge-tracing work can and cannot be trained on.

---

## 1. Headline

> **There is no dataset suitable for training a knowledge-tracing model, and Batch A+B did not
> create one.** What Batch A+B created is the *instrumentation* that makes a valid dataset
> collectable from this point forward.

## 3. Data classification — this is the important section

Every interaction currently in the database falls into one of three classes. **None of them is
real production training data.**

### Class 1 — Synthetic demo data *(the majority)*

Generated by `manage.py demo_adaptive`. This command constructs a scripted learner who is strong
on one section and weak on two, in order to demonstrate the adaptive loop.

Three properties disqualify it as training data:

1. **The outcomes are scripted, not observed.** Correctness is decided by the demo script, not by a
   person answering a question. It encodes the behaviour the system was designed to show.
2. **It writes `AttemptAnswer` rows directly through the ORM**, bypassing the API submission path
   entirely. It therefore has no `answered_at`, no latency, and never passes through the
   offered-set contract.
3. **It is destroyed and recreated on every run.** `demo_adaptive` wipes and rebuilds `SOP-DEMO`.
   The interaction count fell from 60 to 51 to 33 across three runs during this programme. **The
   corpus is not stable, and nothing accumulates.**

> Point 3 alone means the current database cannot be treated as a growing dataset. It is a demo
> fixture.

### Class 2 — Historical API interactions without temporal information

Rows written through the real submission path before `answered_at` existed. They carry a valid
learner, question, correctness and selected option, but **no timestamp**.

They were deliberately **not backfilled**. `answered_at` is nullable and set explicitly in code
rather than declared `auto_now_add`, precisely so the migration could not stamp every historical
row with its own run time and invent a response history that never happened.

**Usable for:** aggregate accuracy per section (which the current adaptive engine already uses).
**Not usable for:** anything ordered by time, elapsed-time features, forgetting curves, or
temporal train/test splitting.

Ordering these rows by `id` is a proxy for time, not a guarantee.

### Class 3 — Interactions recorded under the new contract

Rows written through the API after Batch A+B. These carry a server-set, timezone-aware
`answered_at`, an optional client-reported latency, and belong to an attempt whose offered set was
recorded before the learner saw it.

**Count today: 0**, because the only submissions since the migration were adversarial probes on a
throwaway test database. Every future submission through the UI or API produces Class 3 data.

## 4. What Batch A+B changed for KT specifically

| Property | Before | After |
|---|---|---|
| Interaction ordering | `-id` auto-increment proxy | Server-set `answered_at`, timezone-aware |
| Response latency | Not captured | Optional, validated, explicitly untrusted |
| Trustworthiness of correctness | A modified client could omit or substitute questions | Submission must match the recorded offered set exactly |
| Assessment composition | Not recorded | `QuizAttemptQuestion` records what was offered, in order |
| Reproducibility of an attempt | Impossible | Offered set + order + per-answer time |

The third row matters most. **Training a model on data a client could partially fabricate would
have been the deeper error** — worse than having too little data, because the resulting model
would look trained while encoding manipulable inputs.

## 5. Distance from what published KT models require

| Model | Typical training data | This deployment |
|---|---|---|
| BKT (per skill) | Hundreds of interactions per skill | ~1.6 per chunk |
| PFA / logistic | 10³–10⁴ interactions | 33 |
| DKT | ~5×10⁵–10⁶ | 33 |
| SAKT / SAINT / AKT | 10⁵–10⁷ | 33 |

The gap is **three to four orders of magnitude**, and the usable subset is smaller still: 0 rows
currently carry a timestamp.

## 6. Additional structural gaps for KT

Beyond volume, these remain open and are **not** addressed by Batch A+B:

| Gap | Consequence |
|---|---|
| **No concept layer** (L15) | The unit is the physical chunk. Two chunks covering one concept are tracked independently; mastery does not transfer. KT models keyed on skills would treat them as unrelated |
| **No SOP versioning** (L2) | A chunk's identity is not stable across a document revision, so a longitudinal sequence could silently change meaning |
| ~~Difficulty is live, not snapshotted~~ | **CLOSED 19 Aug 2026.** `AttemptAnswer.question_difficulty_at_answer` and `.learner_ability_at_answer` capture both ratings before `apply_elo_update()` runs. Rows written earlier remain NULL and stay excluded from any difficulty-aware analysis |
| **No knowledge-state or prediction columns** | Deliberate — no model exists. Adding them now would be speculative schema |

Difficulty-when-answered is now recorded for every new interaction. Note the boundary precisely:
interactions written **before 19 Aug 2026 remain NULL** and cannot be used for any difficulty-aware
analysis. Joining today's `Question.elo_rating` onto those older rows would reintroduce exactly the
look-ahead bias this field exists to prevent.

---

## 7. What a valid dataset would require

1. **Real learners answering real assessments** through the UI — not `demo_adaptive`.
2. **A stable corpus.** Demo data must be excluded from any training set, and the demo command must
   stop being the main data producer.
3. **Enough volume.** At minimum hundreds of interactions per learner for an interpretable model
   (BKT/PFA); orders of magnitude more for anything neural.
4. **A concept layer**, so sequences are keyed on something more meaningful than a physical chunk.
5. ~~Difficulty snapshotting~~ — **done**; applies to interactions recorded from 19 Aug 2026 onward.

Until (1) and (2) hold, any reported KT metric would describe the demo script rather than learning.

---

## 8. Conclusion

**Transformer knowledge tracing is architecture-ready but cannot be validly trained on the
available data.** So is BKT, and so is a logistic baseline.

**The evaluation harness now exists** (Batch C, `attempts/evaluation.py`,
`manage.py evaluate_adaptive`). It performs leakage-safe per-learner temporal splitting and
compares the current rule engine, an Elo predictor and a logistic/PFA baseline.

Run against the current database it reports:

```
Status: INSUFFICIENT_DATA
  0 usable of 51 rows (51 no timestamp, 0 no snapshot, 0 short sequence)
  blocked: evaluation split has 0 interactions, below the 100 required
  blocked: minority class has 0 observations, below the 20 required
  blocked: 0 learners with usable sequences, below the 5 required
```

Every row was excluded for lacking `answered_at` — they are `demo_adaptive` output, written
directly through the ORM. This is the corpus-instability problem in §3 demonstrated by the
harness itself: the nine genuinely timestamped interactions recorded through the browser on
19 Aug were destroyed by the next demo rebuild.

So the position is now precise rather than merely asserted: **the instrumentation is valid, the
measurement infrastructure is verified, and there is no data to measure.** Recording a metric
today would be measuring a fixture. The blocker is data collection, not modelling.
