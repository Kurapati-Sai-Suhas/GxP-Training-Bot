## Day 1 — Close the core loop (SOP → AI quiz → review) — ✅ DONE

This is the highest-value day: it directly proves the PS053 claim ("generates role-specific quizzes from SOPs and explains wrong answers").

- [x] **1.1 AI generation endpoint** — `POST /api/ai_engine/generate/` (`backend/ai_engine/views.py`, wired in `ai_engine/urls.py` and `config/urls.py`). Body: `{ sop, job_role, count, difficulty }`. Splits `count` across the SOP's chunks, calls `generate_questions()`, and persists `Question` (status="draft") + `Option` rows.
  - Offline mock generator (`generate_mock_questions` in `ai_engine/services.py`) kicks in automatically whenever `OPENAI_API_KEY` is unset or the live OpenAI call throws — verified by curl with no key configured. This is your demo insurance policy.
- [x] **1.2 Generate Quiz page — real wiring** (`frontend/src/App.jsx`) — SOP/job-role dropdowns now come from `getSopDocuments()`/`getJobRoles()`, generation hits the real endpoint, preview renders real questions with a badge when the offline generator was used, and "Send to Review" navigates to Question Review where the drafts are already sitting.
- [x] **1.3 SOP upload — real wiring** (`SopLibrary` in `App.jsx`) — real form (title/sop_code/version/department + file input) posts multipart to `/api/sops/documents/`, then auto-calls `/process/`. Verified via curl with a real `.txt` SOP: upload → extract → chunk → generate all worked.
- [x] **1.4 End-to-end smoke test** — done via curl + live browser: uploaded a real SOP, processed it, generated 5 questions, reviewed and approved one in the UI, confirmed status flips to "Approved" and persists.

**Bugs found and fixed while wiring this up (pre-existing in the scaffold, not introduced today):**
1. `sops/views.py` `process()` reported `chunks: 0` even when chunking succeeded — `sop.chunks.count()` was reading a stale Django prefetch cache from the `SOPDocumentViewSet` queryset (fetched before the new chunks existed). Fixed by counting via `SOPChunk.objects.filter(sop=sop).count()` instead.
2. The mock generator originally always picked the same first sentence because the view called it once per question (`number_of_questions=1`) in a loop, resetting the generator's internal index every time. Fixed by batching: the view now asks each chunk for its whole share of questions in one call, so the generator can vary sentences within a chunk.

**Known limitation:** the Browser-based smoke test could drive everything except the native OS file picker (no file-upload capability in this tool), so the "select a file" click itself wasn't automated — but the exact code path it triggers (multipart upload → `/process/`) was verified directly against the running backend with a real file.

**End of Day 1 checkpoint:** you can demo "upload an SOP, get an AI quiz draft, review it" without touching Django admin. ✅ Confirmed working.

**Bugs found and fixed while wiring this up:**
1. **Real bug, found via live UI testing:** `attempts/views.py`'s `submit()` action returned a response where `answers` was always empty and every question showed "Not answered" — even though the score and DB rows were correct. Same root cause as Day 1's chunk-count bug: `QuizAttemptViewSet.queryset` prefetches `answers` in `get_object()`, then `submit()` deletes and recreates the answers, so the serializer at the end was still reading the stale (pre-delete) prefetch cache. Fixed by re-fetching the attempt from `self.get_queryset()` right before serializing the response.
2. **Not a bug — a testing artifact worth recording:** an early automated run showed "0 of 0 correct" for a fully-answered quiz. Root cause was my own test script clicking an answer and Submit in the *same* synchronous JS call, so React's batched state update for the last answer hadn't flushed before `handleSubmit` read `answers`. A real user physically clicking two separate buttons can't trigger this (each click is a separate browser event; React flushes between them). Confirmed by re-running with normal per-click pacing — worked correctly, 100% score with all 4 answers recorded.

## Day 6 — Full adaptive retraining, literature-grounded — ✅ DONE

Scope: close the "full adaptive retraining" gap named at the end of Day 5 — not just recommending a weak SOP (already done), but a real scheduling system deciding *when* a learner is due for a retest and *whether* they've mastered a topic. Done as a second, deeper literature pass specifically on spaced-repetition/knowledge-tracing algorithms (22 sources — classic and modern spaced-repetition scheduling, Bayesian/deep knowledge tracing, adaptive item selection, and controlled evidence from professional/clinical training contexts), then a single opinionated, buildable architecture chosen from it.

- [x] **6.1 Literature review and algorithm selection** — the load-bearing citation: Wilson, Karklin, Han & Ekanadham (EDM 2016) directly benchmarked Deep Knowledge Tracing against simpler Bayesian/IRT models and found the simpler models matched or beat DKT, especially at fine content granularity, while needing far less data. That's the empirical basis for explicitly rejecting Bayesian Knowledge Tracing (Corbett & Anderson 1994), Deep/attention-based Knowledge Tracing (Piech et al. 2015; Ghosh et al. 2020), Half-Life Regression (Settles & Meeder 2016 — Duolingo) and SSP-MMC (Ye et al. 2022) — all of which need hundreds to millions of logged responses per skill to fit, far more than a training-bot deployment this size generates — in favor of a **Leitner-style box scheduler** (Leitner, 1972) plus a **streak-based mastery threshold** (a discrete approximation of the Bayesian stopping rule in Sapountzi et al. 2021) and **difficulty-matched item selection** (the T-SKIRT/Knewton approach, Ekanadham & Karklin 2017), reusing the `Question.difficulty` field that already existed. A controlled study in nurse-anesthesia training (Khalafi et al., *BMC Medical Education* 2024) provided direct evidence, from a regulated clinical-training context structurally close to GxP, that spaced re-testing improves retention — supporting the premise without needing algorithmic sophistication to see the benefit. No peer-reviewed paper was found evaluating adaptive retraining specifically in GxP/pharma compliance training — noted explicitly as a real gap and this project's actual contribution angle, not glossed over.
- [x] **6.2 Design decision, checked with the user first** — "auto-assigned" has two readings: silently pre-creating a live `QuizAttempt` ("hard" assignment), or surfacing a due topic prominently while the learner still starts it themselves through the existing flow ("soft" assignment). Given the explicit instruction to change nothing about the existing problem statement or architecture, soft assignment was chosen — it required zero changes to `QuizAttempt` creation semantics, `attempts/views.py`'s `submit()`, or any existing test.
- [x] **6.3 `TopicMastery` model** (`attempts/models.py`) — one row per (learner, SOP): `box_index` (Leitner box, expanding review intervals 1/2/4/7/14/30 days), `streak_correct`, `mastery_status` (`in_progress`/`mastered`, flips after 3 consecutive correct with no intervening miss, re-opens on a later wrong answer), `next_eligible_at`. New migration (`attempts/0002_topicmastery`), no changes to `QuizAttempt` or `AttemptAnswer`.
- [x] **6.4 Signal-driven updates, not a modified view** — `attempts/signals.py`, a `post_save` receiver on `AttemptAnswer`, wired up via `AttemptsConfig.ready()`. `attempts/views.py`'s `submit()` action was not touched at all; the signal fires automatically as a side effect of the existing `AttemptAnswer.objects.create()` calls already in that method.
- [x] **6.5 `GET /api/attempts/auto-assigned/`** — new function-based view, new URL, reads `TopicMastery` live (no scheduled job, no Celery beat needed — matches the project's existing "works with nothing extra running" philosophy) and returns every SOP due for the requesting learner with a difficulty-matched suggestion and a human-readable reason.
- [x] **6.6 Frontend** — an "Adaptive Retraining Due" card on Learner Quiz, above the existing "Recommended Refresher" card (both kept, they answer different questions — "what's scheduled" vs. "what have you personally missed most, ever"). Its button sets the SOP selector exactly like the refresher card already did; quiz start still goes through the untouched `createQuizAttempt` → `POST /api/attempts/quiz-attempts/` path.
- [x] **6.7 Tests** — 6 new tests in `attempts/tests.py`: mastery creation/advancement on correct answers, reset on a wrong answer, mastered topics excluded from the due list even if scheduled, not-yet-due topics excluded, auth required, and cross-learner isolation (RBAC-style — one learner's due topic must not leak into another's list). 51 backend tests total, all passing.
- [x] **6.8 Live verification, not just the test suite** — ran the real dev server, manually seeded a due `TopicMastery` row via `manage.py shell` (spaced intervals mean nothing is naturally "due" minutes after being created, so this was necessary to see the card render), confirmed the card appeared with real data, clicked through "Start Retraining" → real `POST /api/attempts/quiz-attempts/` (201) → answered a real 4-question quiz → real `submit()` (200) → confirmed via shell that the `TopicMastery` row updated correctly from the real submission (reset to box 0 since at least one answer was wrong), and confirmed zero console errors throughout.

**End of Day 6 checkpoint:** full adaptive retraining (soft assignment) is built, literature-grounded, tested, and verified live end-to-end — without a single line of existing model, view, serializer, or test logic being modified to make room for it. ✅ Confirmed working.
